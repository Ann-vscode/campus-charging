# 校园共享电动车移动集群充电仿真系统 — 项目汇报

> 汇报日期：2026-11-20 ｜ 当前进度：P0–P3 完成（11/25 个任务），P4 前端完整阶段待启动
> **仿真声明：本系统所有车辆、电量、位置、能耗与运营数据均为程序生成的仿真数据，不接入任何真实车辆或运营系统。**

***

## 一、项目是什么

面向校园场景的一套**移动集群充电仿真系统**：30 辆共享电动车分散停放在 A/B/C 三个停车区，车辆通过物联网协议上报位置与电量；后端平台自动筛选出每批最多 5 辆低电量车；一台搭载 5 路独立充电通道的移动机器人自主导航前往停车区，完成对接、充电，电量不足时自动返回基站补能；前端实时监控全过程。

**核心要验证的问题**：在有限充电资源下，"机器人移动过去充电"这一调度模式是否可行、效率如何——全部在仿真环境中回答，不接触真实车辆。

***

## 二、从 Idea 到落地的整体思路

### 1. 需求收敛

| 砍掉的需求       | 原因                 |
| ----------- | ------------------ |
| 车辆自动驾驶归位    | 假设电动车已经成排排列好       |
| 真实自动充电机械臂设计 | 机械设计风险不可控，改为对接抽象模型 |
| 真实高功率充电 ，接口 | 安全与合规不可行，全部仿真替代    |

收敛后的系统不再有"让电动车自己脱困"和"人工确认连接"这类自相矛盾的环节，仅侧重于

### 2. 契约冻结：接口先行，三轨并行

项目最关键的方法论决策：**在写任何业务代码之前，先冻结全部公共契约**——

* `contracts/api.md`：12 个 REST 端点 + WebSocket + MQTT 主题，带版本号 v1.0.0；

* `contracts/telemetry.json`：遥测数据 schema；

* `contracts/state_machines.md`：机器人 8 态 / 车辆 7 态 / 充电通道 5 态；

* `contracts/simulation_params.md`：能源、调度权重、充电功率等全部参数。

契约冻结后，后端、机器人仿真、前端三条线**同时开工、互不等待**：前端对着 Mock API 开发，机器人线对着状态机开发，到 P5 集成时只通过契约汇合。任何接口变更必须走 `[CONTRACT]` 变更 PR + 三轨评审。

### 3. Mock 先行：最小闭环验证全链路

不依赖 ROS 2，先用纯 Python 的 MockRobot 把"车辆上报 → 调度选车 → 导航 → 对接 → 五路充电 → 返基站"整条链路在内存里跑通。这样即使机器人仿真环境没搭好，后端逻辑和前端展示也都能先验收。

### 4. 多 Agent 分工：目录隔离 + 任务卡驱动

* 每个 R 任务 = 一张任务卡 + 一个分支 + 一个 PR，写明"允许修改的目录 / 禁止修改的目录 / 验收条件"；

* 协调层（Kimi）负责任务拆分、契约守护、集成验收与文档；

* 实际执行采用主代理 + 内置子代理按目录隔离并行（后端、前端、机器人三线）；

* 每完成一个任务必须交付：可运行代码 + 测试 + README + 已知问题，禁止只交设计图。

### 5. 验收驱动：每个任务都有可运行的判据

不接受"我觉得做完了"。每个 R 任务的验收都是可复现的数字：pytest 用例数、导航到达次数、到达误差（米）、能耗百分比。

### P0 — 冻结需求与场景（完成）

* `docs/project_scope.md`：明确仿真边界，画出车辆上报调度、机器人导航充电、低电量返站三张流程图；

* `scenarios/campus_basic.yaml`：1 个基站 + A/B/C 三停车区（12/10/8 车位）+ 30 辆车 + 道路与静态障碍；**改配置文件即可改车辆数和初始电量，不需要改业务代码**。

### P1 — 接口冻结与最小闭环（完成）

* R1.1：四份契约文件全部冻结，补齐了原方案 6 个缺口（能源参数、调度打分公式、仿真时钟倍速、接口变更治理、跨区补位规则、品牌中性化）；

* R1.2 后端：FastAPI 实现 12 个端点 + WebSocket + MockRobot 状态机 + 五路独立充电 + 能源模型，pytest **14/14 通过**；

* R1.3 前端：React 18 + TypeScript + Vite，17 个文件，含校园地图 / 任务面板 / 五路充电卡片 / 控制条 / 事件日志，Mock 模式一键演示全流程，`tsc + vite build` 通过。

### P2 — 物联网车辆模拟与调度算法（完成）

* R2.1 遥测模拟器：30 辆虚拟车经 MQTT（Mosquitto + Paho）周期上报，支持离线 / 数据过期 / 低电量模拟，实测 29/30 帧上报（A03 按设定离线）；

* R2.2 调度器：按区聚类 + 四维打分（低电量 0.35 / 区域均电 0.20 / 距离 0.25 / 机器人余电 0.20）+ 跨区补位 + 能源守门，**27 个测试用例全过**，同 seed 结果完全可复现；

* R2.3 能源模型：移动按实际位移扣能、充电折算效率与传输损耗、低电量自动返基站补能，**14 个测试用例全过**；

* 过程中修复一个真实 bug：倍速越高能耗越大的积分偏差（10x 倍速下首段耗电被放大 10 倍），改为按实际插值位移积分后，1x/10x/60x 能耗完全一致。全量回归 **72/72 通过**。

### P3 — 机器人导航仿真（完成，本轮新交付）

在 WSL2 + ROS 2 Humble + Gazebo 11 环境中：

* **R3.1 Gazebo 场景与机器人模型**：`campus.world`（三停车区 + 5 充电桩 + 基站 + 路障，与场景 YAML 按 1:10 缩放对齐）+ 自包含差速机器人（差速驱动 / IMU / 激光雷达插件），headless 实测 spawn 成功，`/cmd_vel`、`/odom`、`/scan`、`/imu` 四话题齐全；

* **R3.2 Nav2 点到点导航**：静态地图 + costmap + RPP 控制器，基站 → A/B/C 三区各 3 次共 **9/9 次到达**，最大到达误差 0.191 m；

* **R3.3 动态路障与重规划（含"设置路障"功能）**：

  * 绕障组：道路中插入 0.5 m 方块，**3/3 绕障到达**，最小体表间隙 0.08 m、无碰撞，中途平均 34.7 次重规划；

  * 完全阻断组：16 m 隔墙封路，**0/2 到达**，规划器持续报 `failed to create plan` 并在超时后明确失败——不无限等待，作为"不可达"行为正确的证据；

  * **前端可点面板手动放路障**：控制条"添加临时路障"按钮 → `POST /api/demo/obstacle`，出发前在 (7.0, 2.62) 放置方块后，基站 → B 区绕行到达，误差 0.182 m、最小间隙 0.93 m，演示动图与截图已存入 `results/figs/`。

**口径边界（诚实说明）**：R3.3 目前为"静态插入路障"，尚不含移动障碍；机器人仿真线（Gazebo/Nav2）与后端软件线尚未打通，"真实导航驱动的自动充电"属于 P5 的 R5.1 任务。

## 六、过程中最值得分享的三条经验

1. **契约冻结是多 agent 协作的地基**。接口未定就并行开发，等于给每个 agent 发了一张画错的地图。本项目三条线零等待并行，靠的就是 v1.0.0 契约 + 变更评审机制。
2. **静态配置与动态状态必须分离**。调度器初版直接读场景 YAML 里的静态车辆表，导致充满电的车被重复派单 313 次；改为传入运行时状态视图后修复，并加了回归测试。这是"仿真系统最容易踩、也最容易被忽视"的一类 bug。
3. **验收要数字，不要感觉**。"导航能用"不是验收，"三区各 3 次共 9/9 到达、最大误差 0.191 m"才是；"能绕障"不是验收，"绕障 3/3 到达且完全阻断 0/2 正确报告不可达"才是——**失败行为的正确性和成功行为一样需要验收**。
